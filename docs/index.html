Living PRD (Product Requirements Document)

Updated every week as we test with real users and learn what works.

1. Target User & The Job to Be Done

Problem: Busy people often take 24–72+ hours to reply to texts. Slow replies hurt relationships and work, and the pile of unanswered texts adds stress and guilt that makes replying even harder.

Who is this for? Carly, a friend who is a very busy working professional as a consultant and a slow responder.

The painful "Before" workflow: A text arrives. Carly is busy, so it sits for 24–72 hours while more pile up. Replying starts to feel like a chore, and family, friends, and work contacts are left waiting.

The "After" workflow with this product: A text arrives. Ghostwriter sorts it as Family, Friends, or Work/serious, drafts a reply in Carly's own style, and sends it within that bucket's reply window if it's confident enough. Anything it doesn't send stays unread in Messages, so unread means "this needs you."

2. Scope & Explicit Non-Goals

  • In Scope (Core Workflow):
    1. A new iMessage arrives.
    2. The agent sorts it into Family, Friends, or Work/serious.
    3. It drafts a reply in the user's style for that bucket.
    4. If its confidence meets the bucket's requirement, it sends the reply within that bucket's reply window.
    5. If not, it saves the draft for the user to approve and leaves the message unread.
  • Out of Scope #1: Group chats
  • Out of Scope #2: Other messaging apps (WhatsApp, Android SMS)
  • Out of Scope #3: Replying to scheduling messages (plans, times, dates)

3. How I'll Know It Works

  • Median reply time drops from 24–72 hours to within each bucket's reply window.
  • Under 5% of auto-sent messages are edited, unsent, or flagged as wrong.
  • Under 10% of messages are put in the wrong bucket.

Build 1 · Nov 5–8, 2026

  • What works: A local prototype (prototype/index.html) that takes a pasted text message and shows its bucket (Family, Friends, or Work/serious), a draft reply, a confidence score, and whether it would auto-send or save a draft. All 6 sample messages tested, covering all three buckets and both outcomes. The Product Page is live with PRD v1.
  • What I learned: As I build more, I'll have to work around Apple's limits on outside apps or AI agents sending iMessages on someone's behalf. I also need to decide whether people should be told when a reply was written by AI.
  • What broke or changed: My first GitHub org invite expired and had to be resent. Installing Claude Code failed with a permissions error, which I fixed by having npm install to a folder in my home directory. The repo rename to tms556-ghostwriter didn't go through, so it stays tms556-sandbox. In the prototype, keyword sorting is crude: messages with no keywords default to Work/serious, and the drafts are canned replies, not written in the user's style.
  • Costs: $0 extra. Claude Code ran on my existing Claude Pro subscription (about 3% of the weekly limit). No API keys or paid services. GitHub Pages hosting is free.
  • Hours: ~9.25
  • What's next: Replace keyword sorting and canned replies with a real AI model, install PostHog, add costs to PRD v2, and look into what Apple allows for reading and sending iMessages.
